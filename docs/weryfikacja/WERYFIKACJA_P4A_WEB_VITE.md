# P4a.1 — Vite i wstępna inwentaryzacja web

Stan 2026-11-10, gałąź `codex/v1-p4a-web`, baza `0b3a66acb1f0c249950c3c301f46a841b6f00ace`; pobrany `origin/main` i RC1: `6aa84d8129b7f7cc4d92c3c00b4d8a99a255d3eb`. P4a pozostaje **w trakcie**.

## Zależność Vite — BL-02

Przed zmianą `npm audit --json --ignore-scripts` zgłosił jeden HIGH dla Vite 7.3.6. Wersję przypięto do 7.3.8; diff lockfile obejmuje tylko tę zależność. Wtyczki React i Tailwind rozwiązują ją do tej samej wersji. [Ogłoszenie Vite GHSA-p4f5-76q4-ffq7](https://github.com/vitejs/vite/security/advisories/GHSA-p4f5-76q4-ffq7) z 10 listopada wskazuje 7.3.8 jako poprawioną wersję i opisuje RCE dla serwera developerskiego wystawionego do sieci. Konfiguracja repozytorium domyślnie wiąże serwer z `127.0.0.1`; parametry uruchomienia mogą to zmienić. Sama informacja o dev serverze nie dowodzi RCE w statycznym produkcyjnym dist. Nowe ogłoszenie nie pojawiło się w odczycie npm audit przed zmianą, dlatego nie traktować samego audytu jako kompletnej listy.

Na Windows Node 24.14.0 / npm 11.12.0: `npm ci --ignore-scripts --no-fund --no-audit` PASS, `npm run build` PASS z ostrzeżeniem o dużych chunkach; cztery pliki testów QA 8/8 PASS; lokalne HTTP katalogu PASS. `verify_7_12d.mjs` PASS w odizolowanym Edge: trzy pakiety, R01–R05, harmonogramy, porównanie i round-trip; dowody `outputs/qa/pt_e2e/sol_reference/7_12d/run_m2W7E5/`. `npm audit --json --ignore-scripts` po zmianie: 0 zgłoszeń. To nie dowód braku wszystkich podatności, pełna regresja ani weryfikacja produkcji po aktualizacji. Zależności i źródła advisory należy ponownie sprawdzić przy wydaniu.

Faktyczne żądania i konfiguracja projektu nie zostały tu sprawdzone; nie deklarować braku transmisji danych. Polityka, decyzja o ewentualnych zgodach, test z sentinelami i ocena prawna pozostają otwarte.

SheetJS 0.20.3 jest pobierany z oficjalnego CDN zgodnie z [instrukcją producenta](https://docs.sheetjs.com/docs/getting-started/installation/frameworks/); lockfile zawiera integrity, a `npm ci` powiódł się. Samo powodzenie instalacji i wynik npm audit nie stanowią pełnego niezależnego przeglądu advisory, licencji i pochodzenia. SRI, pełna ocena zagrożeń oraz import/eksport XLSX wymagają dalszej weryfikacji. `vercel.json` nie definiuje nagłówków bezpieczeństwa; nagłówki hostingu nie zostały sprawdzone w tej próbie.

Pozostałe zadania P4a: profil Analytics domyślnie OFF zgodnie z planem i akceptacją właściciela, sieć/sentinela, CSP i workery, privacy, SheetJS/licencje, A→B i odzyskiwanie danych pod kontrolą Sol, produkcyjny test dopiero na odpowiednim kandydacie. Oddzielny hotfix Eko na produkcji nie obejmuje tej aktualizacji.

Przed scaleniem trzeba świadomie przeglądnąć regułę i politykę deploymentu.

## P4a.3 — SheetJS i audyt licencji

16 listopada 2026: `package.json` i lockfile wskazują SheetJS `xlsx` 0.20.3 z oficjalnego CDN. Pobrane przez HTTPS archiwum (2 409 319 bajtów) ma SHA-256 `8dc73fc3b00203e72d176e85b50938627c7b086e607c682e8d3c22c02bb99fe8`; SHA-512 jest zgodne z integrity lockfile. To potwierdza zgodność pobranego archiwum z lokalnym lockfile, nie niezależne podpisanie lub pełną weryfikację łańcucha dostaw. Zainstalowany pakiet deklaruje Apache-2.0, a dołączony plik LICENSE zawiera tę licencję. Weryfikacja obowiązków dystrybucji i prawna pozostaje otwarta.

Według [CVE-2023-30533 producenta](https://cdn.sheetjs.com/advisories/CVE-2023-30533) podatne są wydania do 0.19.2; według [CVE-2024-22363 producenta](https://cdn.sheetjs.com/advisories/CVE-2024-22363) do 0.20.1. Zweryfikowana 0.20.3 leży poza tymi dwoma wskazanymi zakresami. Nie dowodzi to braku innych podatności; pochodzący z CDN pakiet wymaga osobnego monitorowania źródeł producenta i advisory, a nie tylko wyniku npm audit. Importer przyjmuje pliki od użytkownika: ograniczenie 10 MB dotyczy rozmiaru wejścia, limit 5000 wierszy jest sprawdzany po parsowaniu; nie jest to dowód odporności na każdy plik złośliwy lub zasobożerny.

Celowane testy rdzenia XLSX/kolumn 3/3 PASS. `verify_p4a_xlsx.mjs` w odizolowanym Edge zaimportował syntetyczny proces i powiązany BOM, pobrał eksporty XLSX i sprawdził wartości w rzeczywistych plikach, a także pobrał dwuarkuszowy szablon. CDP odnotował pobranie modułu spreadsheets z lokalnego origin, bez zewnętrznych żądań i bez testowego numeru materiału w żądaniach w tej ścieżce. Dowody `outputs/qa/p4a_xlsx/run_dvFuH3/`. Nie obejmuje to wszystkich formatów, nietypowych plików ani hostingu.

Ograniczenie istniejącego `scripts/audit_licenses_and_security.mjs`: kategoria runtime opiera się na bezpośrednich wpisach `dependencies`, a nie zamknięciu przechodnich zależności; skan nie jest pełnym zestawieniem składników rzeczywistego bundle ani dowodem praw do modeli. Jego komunikaty o stuprocentowej zgodności nie stanowią odbioru licencji. Przed wydaniem potrzebny jest kontrolowany inwentarz całego drzewa runtime/build, licencji i notice, analiza artefaktu i ocena obowiązków przez właściwą osobę. Historycznego `outputs/security_audit/audit_7_7.json` nie nadpisano. P4a nadal w trakcie.

Część 158 pozycji build to opcjonalne warianty innych platform, nie lista pakietów wykonanych w bieżącym buildzie. Obecność w domknięciu lockfile nie jest dowodem dołączenia do bundla.

## P4a.5 — analiza archiwum z dołączonymi pakietami

Dodano `scripts/inspect_bundled_licenses.py`: weryfikuje SHA-512 względem lockfile, odczytuje archiwum w pamięci bez wypakowania i uruchamiania, sprawdza nazwy/wersje/licencje oraz szuka plików LICENSE/NOTICE/COPYRIGHT w katalogach pakietów. Powtórzone ścieżki, brak metadanych i niezgodny hash kończą próbę błędem. Testy Python 3/3 oraz inwentarza Node 6/6 PASS. Opcjonalne `npm run audit:licenses -- --package node_modules/@tailwindcss/oxide-wasm32-wasi --archive <plik.tgz>` wymaga Python i wiąże dowód z listą z lockfile; brak danych lub błędny dowód nie zamyka uwagi.

Archiwum `@tailwindcss/oxide-wasm32-wasi` zgodne z lockfile zawiera sześć dołączonych pakietów. Trzy `@emnapi` deklarują MIT i zawierają LICENSE, a `tslib` deklaruje 0BSD i zawiera LICENSE.txt oraz CopyrightNotice.txt. `@napi-rs/wasm-runtime` 1.1.4 oraz `@tybys/wasm-util` 0.10.2 deklarują MIT, lecz nie mają osobnego pliku licencji w swoich katalogach. Oddzielne archiwa tych konkretnych wersji pobrane z npm, zgodne z integrity podanym przez rejestr, także nie zawierają pliku LICENSE/NOTICE/COPYRIGHT według wyszukiwania po nazwach. To obserwacja zawartości, a nie rozstrzygnięcie zgodności licencyjnej ani dowód, że kod tych tarballi jest identyczny z dołączonym kodem.

Po podaniu archiwum inwentarz zgłasza dwie uwagi `bundled_license_file_missing` i kończy się kodem 1; nie podając archiwum zgłasza sześć składników niezweryfikowanych. Dowody `outputs/qa/p4a_license/run_Dt6d4U/inventory.json` i `outputs/qa/p4a_license/bundled/`; archiwa i raporty są lokalnymi materiałami QA. Weryfikator nie analizuje pełnej treści licencji, kodu zagnieżdżonego ani obowiązków notice. Należy ustalić pochodzenie tekstów licencyjnych dla tych wersji i ich zastosowanie do rzeczywistej dystrybucji, z oceną właściwej osoby. P4a/PLAN 7.7 pozostają w trakcie.
